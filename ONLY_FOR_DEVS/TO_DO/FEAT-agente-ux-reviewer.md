### 1.3 Motivação estratégica

- Desde 16/10/2026 há **cliente real em produção**: erro mascarado como vazio ou ação destrutiva com `confirm()` nativo têm custo real de suporte e confiança.
- O produto é PWA + Capacitor — mobile é cenário de primeira classe, e hoje o Playwright só roda `Desktop Chrome`.
- **Decisão já tomada pelo usuário:** nada do catálogo `github.com/davepoon/buildwithclaude` (MIT) será instalado (prompts genéricos, "Use PROACTIVELY" causaria auto-delegação, agentes de implementação conflitam com Firebase client SDK + API routes, `npx skills add` de terceiros é risco de supply chain). Cria-se agente próprio, **reescrevendo** ideias de três fontes (ver §12).
- **Decisões do usuário em 19/10/2026 (§10.1):** D1 = (C) axe + perfil mobile nesta task; D2 = ajustar `ui-consistency-auditor`; D3 = gerar caderno de teste; D4 = primeira auditoria completa em task separada.

## 4. Decisões de Design

### 4.1 Abordagem escolhida

1. **Agente próprio, formato da casa.** `.claude/agents/ux-reviewer.md` estruturado como o `ui-consistency-auditor.md`: frontmatter → papel → bloco "Papel deste agente no fluxo" (estilo `uc-issues-tracker.md:37-53`) → `$ARGUMENTS` → modos → método → formato da saída → regras → entrega.
2. **Documento vivo único** `_PADRAO-UX.md` com IDs estáveis `UX-NNN` (nunca reaproveitados).
3. **Análise híbrida:** estática por padrão (todas as 72 telas) + runtime via axe para as telas listadas em `A11Y_ROUTES` (inicialmente 4). A cobertura runtime cresce por PRs do `qa-agent`/dev, nunca pelo próprio agente.
4. **Infra de acessibilidade = catraca por regra (baseline).** Hoje o sistema já tem violações conhecidas (§1.2); exigir zero violações quebraria o gate de imediato, e o modo só-relatório não protegeria contra regressão. O baseline registra, por `projeto|rota`, o **conjunto de `ruleId`s** já violados; o teste falha só se aparecer regra nova. Regras que somem do resultado geram anotação `baseline-shrinkable` para o dev reduzir o baseline.
5. **Projeto mobile restrito por tag.** `mobile-chromium` roda só `@mobile`; o desktop continua rodando a suíte inteira (inclusive o caderno de acessibilidade). Ver §4.2/§6.5.
6. **Integração por sinalização**, não por edição cruzada.

### 4.2 Alternativas descartadas

| Alternativa | Motivo da rejeição |
|-------------|--------------------|
| Instalar agentes/skills do buildwithclaude | Decisão do usuário (§1.3) |
| Ampliar o `ui-consistency-auditor` para UX | Mistura critérios e documentos; UX exige leitura de fluxo/estado e agora execução de axe |
| Agente com `Edit` que corrige código | Quebra `doc-writer → dev-task-manager` e Git Flow; cliente real em produção |
| Agente gravando no `_MAPA-DE-BUGS-E-MELHORIAS.md` | Mapa é exclusivo do `uc-issues-tracker` (`uc-issues-tracker.md:55`) |
| Gate axe com **zero violações** | Quebra o CI no primeiro PR (dívida existente §1.2) e bloquearia todas as tasks até a correção total |
| Gate axe **só-relatório** (nunca falha) | Não impede regressão; regra 8 pede gate |
| Baseline por **seletor CSS** (`target`) ou allowlist por nó | Seletores com classes Tailwind mudam a cada refactor visual → falsos negativos/positivos frequentes |
| Baseline por **contagem de nós** por regra | Telas com listas (dashboard, inventário) variam de quantidade conforme o estado do emulador, que é mutado pelas specs UC-* rodando no mesmo seed único → flakiness |
| Mobile com `devices['iPhone 13']`/WebKit | Exige `npx playwright install --with-deps webkit` no CI (download extra e mais deps de sistema) e WebKit Linux não equivale ao WKWebView do Capacitor iOS; ganho baixo para o custo |
| Rodar **a suíte inteira** também no mobile | (1) seed roda uma vez e várias specs UC-* mutam estado (aprovar/rejeitar solicitação, criar usuário) — a segunda passada encontraria estado já alterado e falharia; (2) dobra o tempo do job (`workers: 1`); (3) as specs UC-* foram escritas para o layout desktop (ex.: navegação do `ClinicLayout` vira menu colapsado em `md:hidden`) |
| Gate só no desktop, mobile fora do CI | Perde a verificação de reflow/axe mobile como gate, que foi o motivo da decisão D1 |

### 4.3 Trade-offs aceitos

- **Baseline por regra é mais grosso:** uma nova ocorrência de uma regra já presente na rota (ex.: mais um botão sem nome) não quebra o gate. Aceito em troca de estabilidade; o JSON completo do axe fica no artefato e o `ux-reviewer` analisa por nó.
- **Cobertura runtime inicial pequena** (4 rotas, 2 portais): consultor e `clinic_user` ficam de fora porque, no seed atual, têm termos pendentes e caem em `/accept-terms`. Ampliar exige mudança de seed — fora do escopo; o `ux-reviewer` sinaliza ao `qa-agent`.
- **Sem WebKit/iOS:** comportamento específico de Safari/WKWebView não é coberto.
- **Licença MPL-2.0** de `@axe-core/playwright` e `axe-core` (copyleft fraco, por arquivo): aceitável para devDependency usada só em testes e não distribuída no bundle; nenhuma modificação dos arquivos da lib é feita. Registrar no PR.
- **Mapeamento tela ↔ UC é heurístico** (rotas citadas nos UCs).

#### 6.2.4 Checklist — Estados, Acessibilidade, Heurísticas, Textos e Mobile

**Estados obrigatórios** (ideia reescrita de `anti-ui-slop`):

| Estado | O que verificar | Grep inicial |
|--------|-----------------|--------------|
| Loading | Estado de carregamento com `Skeleton`/spinner + texto; sem salto de layout | `loading`, `Skeleton`, `Loader2`, `fallback=` |
| Vazio | Mensagem + próxima ação; distingue "sem dados" de "sem resultado no filtro" (bom exemplo: `consultant/clinics/page.tsx:114-130`) | `length === 0`, `Nenhum`, `Nenhuma` |

| Sucesso | Feedback (toast/redirect/estado atualizado) | `toast(`, `router.push` |
| Desabilitado/processando | Submit desabilitado durante operação; evita duplo clique | `disabled=`, `isSubmitting`, `saving` |
| Sem permissão | Role sem acesso, clínica suspensa/licença inativa, tenant sem dados | `ProtectedRoute`, `allowedRoles`, `role ===`, `suspended` |

```ts
export type A11yMode = 'enforce' | 'report';

export interface A11yScanOptions {
  /** Chave da rota (A11yRoute.key) ou chave ad-hoc para conteúdo sintético. */
  routeKey: string;
  include?: string[];
  exclude?: string[];
  /** Tags extras (ex.: 'best-practice') — só usadas quando mode = 'report'. */
  extraTags?: string[];
}

/** Roda o axe com WCAG21AA_TAGS, grava test-results/a11y/<projeto>/<routeKey>.json e anexa ao testInfo. */
export function scanA11y(page: Page, testInfo: TestInfo, opts: A11yScanOptions): Promise<AxeResults>;

/**
 * Compara os ruleIds violados com a entrada `${testInfo.project.name}|${routeKey}` do baseline.
 * - mode 'enforce' (padrão): falha se houver ruleId fora do baseline.
 * - mode 'report' (A11Y_MODE=report): nunca falha; anota ruleIds novos.
 * - Em ambos: anota `baseline-shrinkable` para ruleIds do baseline que não ocorreram.
 * - A11Y_UPDATE_BASELINE=1: regrava a entrada no JSON; lança erro se process.env.CI.
 * - Se a versão de axe-core instalada ≠ baseline.axeCore: anotação de aviso (regras podem mudar).
 */
export function expectNoNewA11yViolations(
  page: Page,
  testInfo: TestInfo,
  opts: A11yScanOptions
): Promise<void>;

/** Mede overflow horizontal (reflow) e grava test-results/a11y/<projeto>/<routeKey>.overflow.json. */
export function measureHorizontalOverflow(
  page: Page,
  testInfo: TestInfo,
  routeKey: string
): Promise<{ scrollWidth: number; innerWidth: number; overflow: boolean }>;
```

- Ao varrer, aguardar o `readyHeading` da rota (`page.getByRole('heading', { name })`) — nunca `networkidle` (listeners realtime do Firestore mantêm conexão aberta).

### 6.5 Projeto mobile no `playwright.config.ts`

Antes (linha 81):

```ts
projects: [{ name: 'chromium', use: { ...devices['Desktop Chrome'] } }],
```

Depois:

```ts
projects: [
  // Gate completo: todas as specs (UC-*, _infra-*).
  { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
  // Gate mobile: só testes com tag @mobile (somente leitura). Ver FEAT-agente-ux-reviewer §4.2.
  { name: 'mobile-chromium', use: { ...devices['Pixel 7'] }, grep: /@mobile/ },
],
```

- **Device:** `Pixel 7` — engine Chromium (já instalado no CI), viewport 412×839, `isMobile: true`, `hasTouch: true`. Nenhum browser novo; step `npx playwright install --with-deps chromium` inalterado.
- **Nome `chromium` preservado** para não alterar referências/relatórios existentes.
- **Gate de CI — recomendação aplicada:** os **dois** projetos rodam no job `E2E (Playwright + Firebase Emulator Suite)` (status check obrigatório), com o mobile restrito a `@mobile`. Justificativa na §4.2 (estado mutado do seed único, tempo dobrado, specs UC-* escritas para layout desktop). Novas specs só ganham `@mobile` se forem somente leitura ou semearem seus próprios dados.
- **Tags:** usar a API de tags do Playwright (`test('...', { tag: '@mobile' }, ...)`), que o `grep` do projeto casa.
- **Impacto estimado no tempo do job:** login + navegação + varredura ≈ 5–15 s por rota/projeto (primeira visita compila a rota no `next dev`); 4 rotas × 2 projetos + 2 testes sintéticos × 2 projetos ⇒ estimativa **+1 a +3 min**. Medir no PR (RNF-10); se passar de 3 min, reduzir rotas do `mobile-chromium` antes do merge.
